# Architecture

```
┌───────────────────────────────────────────────────────────┐
│ UI: app/macOS, app/tvOS (render FeatureStore state)       │
├───────────────────────────────────────────────────────────┤
│ Features: one state machine per behavior (pure reduce)    │
├───────────────────────────────────────────────────────────┤
│ Domain: values, branded ids, ports (protocols) + errors   │
├─────────────────────────────┬─────────────────────────────┤
│ Adapters/Core               │ Adapters/Aether             │
│  CoreRuntime, Core*Service  │  AetherPlaybackEngine:      │
│  CoreClient (only FFI user) │   PlaybackEngine            │
├──────── FFI (C ABI) ────────┤  AetherEngine (SwiftPM)     │
│ Rust bridge crate (core/)   │                             │
│ stremio-core (pinned rev)   │                             │
└─────────────────────────────┴─────────────────────────────┘
```

## Rust bridge

`core/` depends on `stremio-core` with the `env-future-send` feature, pinned to a commit in `core/Cargo.toml`.

- **Wire format.** JSON in stremio-core's own serde shapes, the same contract `stremio-core-web` uses. Actions are core's `Action` enum; state is a serialized core model; events are core's `RuntimeEvent`. There is no schema to keep in sync by hand. `stremio-core-kotlin`'s protobuf layer was the alternative and costs about 6k lines of mapping.
- **FFI surface.** `core/include/StremioBridge/stremio_bridge.h`. `sb_initialize` (host callbacks + storage directory), `sb_dispatch`, `sb_get_state`, `sb_fetch_resolve` / `sb_fetch_reject`, `sb_bytes_free`. Bytes in, bytes out. `sb_dispatch` also takes bridge requests about what core does not know, such as `{"setAddonEnabled": …}`.
- **Models.** `AppModel` in `core/src/model.rs` lists the core models the app runs: `ctx`, `continue_watching_preview`, `addon_details`, `board` and `search` (two `CatalogsWithExtra`, as in `stremio-core-web`), `discover` (`CatalogWithFilters`, one catalog with an extra such as a genre), `meta_details`, `player`, `link`, `library` (`LibraryWithFilters` over the titles not removed: one type or all, sorted, 100 per page) and `calendar` (the library's shows with their videos, from catalogs that accept the `calendarVideosIds` extra). Adding a line to its `models!` list and a case to `CoreField` in Swift exposes another model. Most fields serialize as core does. `ctx` adds `searchHistory`, the queries searched most recent first, because core leaves its search history out of the state, `disabledAddons`, the add-ons switched off on this device, and `sourceAddons`, the source add-ons the other models list after the enabled ones. `meta_details` adds `watchedVideos`, the ids of the first ready meta item's videos the user has watched, because core leaves its watched bitfield out of the state. `calendar` serializes as `CalendarState`: core's `selected` and its `metaItems`, each show cut to its id, type, name, images and the videos released from a day before the read on, because core holds every video of every show and repeats the month's in `items`.
- **Add-ons off on this device.** Core has no such switch, so the bridge keeps it. `AppModel` implements core's `Model` by hand: `ctx` updates with every installed add-on, so syncing, installing and removing work as before, and every other model updates while `ctx.profile.addons` holds only the enabled ones. The set of transport URLs switched off is saved under `disabled_addons` in the bridge's storage, which core never reads, so it stays off the account. Core's runtime dispatches only core actions, so `setAddonEnabled` queues the change and dispatches `Unload` to `ctx`, which ctx ignores. Every update applies queued changes first, then sends `ProfileChanged` to the other models, which select again: the board drops or regains the add-on's catalogs, and details and streams ask only the enabled add-ons.
- **Add-on order.** Core asks add-ons in `ctx.profile.addons` order, which orders streams, subtitles and the board, but has no action to change it. `setAddonOrder` names every installed add-on once, in the new order. It goes through the same queue, puts the profile's add-ons in that order and sends `ctx` what core sends after an install: `ProfileChanged`, which saves the profile, and for a signed-in account `PushAddonsToAPI`, which syncs the list to Stremio's API and so to other devices. An order that no longer names each installed add-on once, or one for an account whose add-ons are locked, is refused and logged, and the app's request times out.
- **Open Movies.** A fresh signed-out profile, on first launch or after sign-out, lists the built-in Open Movies add-on (`core/src/open_movies.rs`) before core's defaults, so a signed-out user's first row and first streams are Creative Commons and public domain films that play. Its transport URL is under the reserved `.invalid` domain and `fetch::send` answers its manifest, catalog and streams in the bridge; details come from Cinemeta. It is an ordinary installed add-on: it can be reordered, switched off or removed, and signing in replaces it with the account's add-ons.
- **Source add-ons.** The user's own media sources are add-ons the app answers itself, at `https://<source id>.source.invalid/manifest.json`. `{"setSources": {"descriptors": [...]}}` replaces the whole list; a descriptor with another URL, or with an id prefix that is neither `tt` nor `takane-…`, fails the request in `sb_dispatch`. The bridge never saves them and never puts them in `ctx`: every other model sees them after the enabled add-ons, so `addonCollectionSet` cannot push them and a pull cannot drop them, and the app sends them again on each launch. Titles found only on a source have `takane-…` ids and stay on this device: `fetch::send` drops their items from `datastorePut`, answers an all-local put with the API's success, and answers `seekLog`, `getSkipGaps` and the likes API's `send` itself when they name a local title (`core/src/sources.rs`).
- **Trakt scrobbling.** Stremio scrobbles to Trakt on its servers, from the player's analytics events. Core's `analytics` feature stays off, because its debug builds skip the network. Instead `core/src/scrobble.rs` picks the player events (`playerPlaying`, `playerStopped`, `playerEnded`, `traktPlaying`, `traktPaused`) whose context has `hasTrakt`, and sends each as its own `events` request in `stremio-core-web`'s shape. Accounts without Trakt, and titles with a local id, send nothing. Sending is best effort: a failure is logged, not retried.
- **Packaging.** `build/StremioBridge.xcframework` with `macos-arm64`, `tvos-arm64` and `tvos-arm64-simulator` slices. `scripts/build-core.sh` builds it. The Xcode targets `StremioBridge_macOS` / `StremioBridge_tvOS` run that script before the app links and refresh only the slice of the platform being built. The simulator slice is arm64 only, so the tvOS target excludes x86_64 for the simulator.
- **Toolchain.** Nightly, pinned in `rust-toolchain.toml`. tvOS targets are tier 3 and build `std` from source (`-Zbuild-std`), which needs the `rust-src` component.

### `Env` implementation

Core's `Env` trait (`src/runtime/env.rs`) is what the host must provide:

| Method | Implementation |
|---|---|
| `fetch` | Call back into Swift; `URLSession` performs the request and answers with `sb_fetch_resolve` / `sb_fetch_reject`. |
| `get_storage` / `set_storage` | In Rust: one JSON file per key in the directory Swift passes to `sb_initialize` (Application Support on macOS, Caches on tvOS). A read or write starts when its future is first polled, so `exec_sequential` orders writes to one key. |
| `exec_concurrent` / `exec_sequential` | Tokio runtime owned by the bridge; sequential futures run in order on one queue. |
| `now` | `chrono::Utc::now()`. |
| `log` | `tracing`, forwarded with all bridge logs to the Swift logger. |
| `flush_analytics` / `analytics_context` | No-op. |

## App architecture

The app is ports and adapters with a state machine per feature. Dependencies point inward: UI → Features → Domain ← Adapters. `app/Shared/App/StremioApp.swift` is the composition root and the only file that names concrete adapters.

### Domain

`app/Shared/Domain` holds what the app talks about, independent of where it comes from.

- **Values and identifiers.** `PlayableID` (movie, show plus season and episode, or live channel), `MediaID` and `ManifestURL` are parsed once, at the boundary, by failable initializers. Inside the app the type proves the value is valid.
- **`Redacted<Value>`** wraps what identifies the user or grants access: add-on URLs (`ManifestURL.url`, which can carry a debrid key), the account's email (`Account.signedIn`, `EmailAddress`), the sign-in code and its link (`LinkCode`), core's auth key, stream URLs (`PlaybackSource.url`), add-on subtitle files and the log link (`LogLink`). It also wraps what names a third-party add-on, since which add-ons someone uses is their own business: add-on names (`InstalledAddon.name`, `addonName`), catalog names and ids, a stream's name and description, which add-ons fill with their own name, and the tracking token holding the stream as core has it. And it wraps what says what someone watches or looks for: a title's name, year and overview (`MetaPreview`, `ContinueWatchingItem`), episode names and overviews (`Video`, `UpcomingEpisode`, `UpNext`), the player's title, a stream's file name, a subtitle file's label and id, a track's title and subtitle text. `MediaID`, `PlayableID` and `SearchText` render the same way. Their text shows the value, except in a release build's log line, which shows a code standing for it (see [Logging](#logging)); an episode's code keeps its season and episode, `#k3f9qa S1E4`, which alone name nothing. Code that needs the value, a request or text the user must read, takes `rawValue`. `Password` never shows.
- **Ports.** One protocol per capability: `AccountService`, `AddonService`, `CatalogService`, `StreamService`, `LibraryService`, `PreferencesService`, `PlaybackTracker`, `PlaybackEngine`, `SkipSegmentService`, `SubtitleService`, `WatchOfferService`, `LogSharing`, `MediaSourceService`. Each has its own error enum (`AccountError`, `AddonError`, `CatalogError` and `DetailsError`, `StreamSourceError`, `WatchedError`, `PreferencesError`, `PlaybackError`, `SkipSegmentError`, `SubtitleSourceError`, `WatchOfferError`, `LogSharingError`, `SourceError`) and uses typed throws. Changing state is an `AsyncStream` that yields the current value first, then every change.
- **`Remote<Value, Failure>`** (loading, loaded, failed) for anything fetched, and **`Probe`** (pending, done, failed) for one look at changing state while waiting.
- **`TrackingToken`** is the one opaque value: the stream provider puts what it needs to track playback into the candidate it returns and the tracker reads it back. For core that is the player selection JSON.

Catalogs and metadata come from the user's add-ons only. `CatalogService` has one method per capability: `board()` streams the home rows, `loadMore(_:)` pages a row, `search(_:)` streams results across add-ons and records the query in core's search history, `recentSearches()` streams that history and `clearRecentSearches()` empties it (core removes no single entry), `genres()` streams the catalogs of the add-ons on for this device that can be filtered by genre without requiring one (Cinemeta's Popular and Featured, not its New, whose `genre` lists years), `titles(_:)` streams one catalog's first page in one genre (`GenreFilter`), and `details(_:type:)` returns one title with its videos, each marked watched or not, and whether the title as a whole is (meaningful for a movie). `detailsChanges(_:type:)` then streams the same title's details while core holds them, so a mark set on the page or an episode finished in the player shows when it lands in core's state, with no local copy. `LibraryService.setWatched(_:_:)` sets a `WatchedTarget`: a title, a season or one video. On the details page a long press on an episode marks it or its season, and on Play or Resume marks a movie. On a movie in continue watching it marks the movie watched, which ends its progress. A series is never marked as a whole, since core would leave its episodes as they were. Seasons and videos are marked through `meta_details`, so the adapter throws `WatchedError.titleNotLoaded` when core holds another title's details. Poster cards offer no mark: core's `ctx` keeps the library out of its serialized state and the `library` model lists only the library's titles, so a catalog title's watched state cannot be shown.

The library is Stremio's watch list: local while signed out, synced with the account once signed in. `LibraryService.library(_:)` streams the titles of one `LibraryFilter` (a type or all, and a `LibrarySort`) as `LibraryContents`, which names the filter it answers, the types the library holds and whether `loadMoreLibrary()` would add a page. Core holds one filter, so a newer call finishes the older stream. `setInLibrary(_:_:)` adds a title or removes it, and `TitleDetails.isInLibrary` reports it from `meta_details`'s library item, so the details page follows the change with no local copy. `upcomingEpisodes()` unloads and loads `calendar` on every call, since core asks the add-ons only while it holds no shows, and yields the `UpcomingEpisode`s released from the start of the viewer's today on, earliest first: loaded and empty with no calendar add-on or no shows, failed only when every add-on failed. Every title is keyed by `MediaID`, so a stream lookup matches it. A row is one catalog of one add-on (`CatalogRow`), and an add-on that fails fails its own row. Images are the URLs the add-ons give. "Nothing installed" is a state of its own, distinct from loading and from add-ons that answered with nothing: `Board.noCatalogAddons`, `SearchResults.noSearchAddons` and `DetailsError.noMetaAddons`, so screens can tell the user to install a catalog add-on.

### Features

A `Feature` (`app/Shared/Features/Feature.swift`) is a finite state machine:

```swift
enum StreamsFeature: Feature {
    enum State { case idle, lookingUp(PlayableID, results: StreamResults?) }
    enum Event { case lookUp(PlayableID), resultsChanged(StreamResults) }
    enum Effect { case watch(PlayableID) }
    static func reduce(_ state: inout State, _ event: Event) -> [Effect]   // pure: every rule
    static func run(_ effect: Effect, _ dependencies: Dependencies, _ send: …) async   // no rules
}
```

`reduce` holds every rule: legal transitions, dropping stale answers (events carry the request they answer), progress throttling. Tests drive it with plain values. `run` performs one effect against the feature's ports and reports back as events. `FeatureStore<F>` is the `@Observable` runtime views read and `send` to; it starts each effect in a task, cancels them when it goes away and offers `until(timeout:onTimeout:probe)` for tests and the smoke test.

Features today: `PlayerFeature` (idle, active session with phase opening/playing/paused/ended, tracks, add-on subtitles, speed, restoring remembered track choices, skip segments, timeline scans and the up next offer, failed), `AccountFeature` (account, sign-in by code or password, linking Trakt while its code is on screen), `HomeFeature` (continue watching and the board; an item is there because the user stopped partway or because the show has new episodes, and a new-episodes card opens the show's page instead of resuming), `AddonsFeature` (install, remove, and switch on or off on this device, one change at a time), `StreamsFeature`, `PreferencesFeature` (track languages, subtitle style, seek step, hiding spoilers and up next), `SourcesFeature` (the user's media sources: adding, editing and removing, one save and one removal at a time). `AppContext` holds those app-wide stores. `DetailsFeature` (also adding the title to the library), `SearchFeature` (the query and its results, and before anything is typed recent searches and one catalog's genres per content type), `GenreFeature` (one catalog's titles in one genre), `LibraryFeature` (the library's titles for the chosen filter, paging and removing), `CalendarFeature` (upcoming episodes, loaded again whenever the screen appears while the ones shown stay) and `LogSharingFeature` (sharing the logs of a `LogWindow` while Share Logs is on screen; another window keeps the link) belong to the screen that shows them. `ReleaseSchedule` groups upcoming episodes by local day and labels each by its distance from today. `Launch` makes "services are ready" a state: screens exist only in `.ready(AppContext)`, so nothing can send to core before it started.

### Adapters

- **Core account.** `CoreAccountService` signs in through core's `link` model (create a code, poll `ReadData` every 3 s, then `Authenticate` with the key) or with email and password. Core replaces the profile's add-ons on sign-in, so the adapter reinstalls the ones added while signed out; watch progress is the account's. Trakt links as in stremio-web: the QR code opens `https://www.strem.io/trakt/auth/<user id>`, Stremio's site stores the authorization on the account, and the adapter pulls the user (`PullUserFromAPI`) every 3 s until `user.trakt` is present and unexpired (core's own check), then dispatches `InstallTraktAddon`. `LogoutTrakt` unlinks it and removes the add-on. Authentication failures arrive as core `Error` events, which `CoreRuntime.events()` streams. `Authenticate` dispatches and core events are logged with credentials redacted. Core pulls the account's add-ons, library and new episodes only on sign-in, so the composition root calls `AccountService.sync()` and `LibraryService.checkForNewEpisodes()` at launch and whenever the scene becomes active. `sync()` dispatches `PullUserFromAPI` (which signs out an expired session), `PullAddonsFromAPI` and `SyncLibraryWithAPI` (which also pushes progress a failed upload left behind) only when signed in, since core answers each with an `Error` event signed out. `checkForNewEpisodes()` dispatches `PullNotifications`, which core rate-limits to every 6 hours.
- **Core.** `CoreClient` is the only code that touches the FFI. `CoreRuntime` turns core's protocol (dispatch an action, later receive `NewState` naming the changed fields) into async APIs: `states`/`observe` stream a field's state (current first), and `request` subscribes, dispatches and waits until a probe accepts a state. No polling. Because the current state is probed first, every probe checks that the state answers its own request (transport URL, selected stream path). `CoreAddonService`, `CoreCatalogService`, `CoreStreamService`, `CoreLibraryService`, `CorePlaybackTracker` and `CoreSubtitleService` implement the ports. `CoreRuntime.load` loads a selection into a model and streams the states that answer it, finishing once another load replaces it. `CoreAction.swift` encodes actions, `CoreDispatchRequest.swift` the document `sb_dispatch` takes, bridge requests included, and `CoreResources.swift` the resource requests and catalog and library selections they carry; `CoreWire.swift`, `CoreWirePlayer.swift`, `CoreWireLibrary.swift` and `CoreWireTrakt.swift` decode only the fields the adapters read, and `CoreUpcomingEpisodes.swift` maps the calendar to `UpcomingEpisode`s. Core keeps one `meta_details` selection, so a new stream lookup replaces the previous one and finishes its stream.
- **Add-ons answered in the app.** `CoreInProcessAddons.swift` holds the Core adapter's two hooks for source add-ons. `CoreClient` sends every request core makes for a URL under `.source.invalid` (`InProcessURL`) to `CoreInProcessAddons` instead of the network. Such an add-on gives core placeholder stream and subtitle URLs, and `CorePlaybackLinks` turns each into the file the player loads, headers included, when `CoreStreamResults` builds a candidate, `CoreSubtitleService` lists a file and the tracker and subtitles match core's selection. Core's state, its `streams` bucket and remembered subtitle choices keep the placeholder, so they hold no credential. `CoreRuntime.setSources` lists the add-ons (`SourceAddonDescriptor`). Debug builds launched with `STREMIO_FIXTURE_SOURCE=1` put `FixtureSource` in place of the user's sources: one such add-on answered from memory over the dev WebDAV server (`scripts/dev-sources.sh up`).
- **Media sources.** `Adapters/Sources` implements `MediaSourceService`. `SourceLibrary` signs in before it keeps a source (`JellyfinClient`: `AuthenticateByName` after checking `/System/Info/Public`, with one device id per source; `WebDAVClient`: `PROPFIND` with `Depth: 0`), keeps each in the Keychain (`KeychainSourceStore`: one this-device-only item per source, the Jellyfin token or the WebDAV password as its data, never Jellyfin's password), and lists one add-on per source in core with `setSources` at launch and after every change. For now each answers its manifest only. The data protection keychain never prompts, so an ad hoc signed macOS build, which lacks the entitlement it needs, fails to store a source (`errSecMissingEntitlement`) instead. Debug builds launched with `STREMIO_SOURCES` (a JSON array of `{kind, url, username, password}`) add those sources through `add` at launch, skipping ones already stored.
- **Core catalogs.** `CoreCatalogService` loads `board` with every catalog without a required extra and `search` with every catalog that accepts the `search` extra. These are core's rules, and the adapter does not repeat them. Once core holds the selection, an empty `catalogs` list means no add-on offers one. Core lists catalogs without fetching them, on load and again when the profile's add-ons change, so the adapter asks for them with `LoadRange`. That is how an install shows up on the board without another load. `titles(_:)` loads `discover` with the catalog request and its `genre` extra; core fetches that one page and, unlike a `search` load, adds nothing to the search history. `details` loads `meta_details` with no stream path. A stream lookup for the same title, such as an episode of that show, reuses the metadata it loaded. A details call replaces a running stream lookup. `scripts/smoke.sh --no-addons` starts core without its default add-ons (`EMPTY_OFFICIAL_ADDONS=1`) and checks the empty states, then installs Cinemeta and checks that the open board stream fills.
- **SkipDB.** `SkipDBSkipSegmentService` conforms to `SkipSegmentService` over the open SkipDB API (skipdb.tv, no key): recap, intro, outro and preview ranges for an IMDb id, fitted to the stream's duration and clamped to it. It shares `URLSession.json` (`Adapters/HTTP`) for requests, logging and the `HTTPFailure` it maps to `SkipSegmentError`. The `StremioTVAdapterTests` target tests it against recorded responses through a `URLProtocol` stub; set `TEST_RUNNER_STREMIO_LIVE_TESTS=1` to run its live tests too.
- **IntroDB.** `IntroDBSkipSegmentService` conforms to `SkipSegmentService` over the IntroDB API (introdb.app, anonymous reads, rate limited): crowdsourced recap, intro and outro ranges for an IMDb id. It takes no duration, so each range's fit is unknown and only clamped to the stream; a 404 means no data. `Services.skipSegments` returns the service for the source in the preferences. That choice stays on the device: `CoreDeviceSettings` keeps it in `UserDefaults`, because core's profile settings drop keys they do not know, and stores nothing for a source equal to the default, so the default can follow the account. `SkipSegmentSource.resolved` holds the rule: with nothing chosen, Stremio's own for a Stremio Premium account and IntroDB otherwise; a stored Stremio without Premium reads as IntroDB, and Settings offers Stremio only with Premium.
- **Streaming Availability.** `StreamingAvailabilityWatchOfferService` conforms to `WatchOfferService` over the Streaming Availability API (movieofthenight.com through RapidAPI, keyed): the services that offer an IMDb id in the device's region, one `WatchOffer` per service with its link and the lowest rent and buy prices. A series gets its show's offers, not each episode's. The key allows few requests a month, so answers are kept per `MediaID` for the life of the process; 404 (unknown title) and 400 (country not covered) mean no offers. The key reaches the app through the `RAPIDAPI_KEY` build setting from the git-ignored `Secrets.local.xcconfig` (see `Secrets.xcconfig`) into the `RapidAPIKey` Info.plist entry. Builds without it, release IPAs included, get no `WatchOfferService` requests: `Services.live` puts in one that finds nothing. `StreamsFeature` looks offers up only for a signed-out account, and the stream list shows them under Other Services, each opening its link.
- **Core skip gaps.** `CoreSkipSegmentService` reads Stremio's own skip times from core's `player` model. Core asks Stremio's API by itself for a Premium account once the player holds an episode's stream, the OpenSubtitles hash `CoreSubtitleService` reports and a duration, then sets `introOutro`, fitted to that duration. Core does not expose whether it is still asking, so the adapter takes the first `introOutro` for the selected item, or no segments after 30 s, and none at once for a movie. `Profile.hasPremium` is core's own check (`premium_expire` after now), which `Account.signedIn` carries.
- **Local network.** `LocalLogServer` conforms to `LogSharing` with a Network.framework listener: port 8080, or any free port when it is taken, and a random 4-character path (no 0, o, 1, l or i), so the address is short to type: `http://192.168.1.20:8080/k7fm`. Only `GET` of that path answers, with `Log.export` of the window shared at request time as a `.log` download; anything else is a 404. The address is the first up, non-loopback IPv4 interface, `en0` first. `NSLocalNetworkUsageDescription` explains the access.
- **Aether.** `AetherPlaybackEngine` conforms to `PlaybackEngine` over [AetherEngine](https://github.com/superuser404notfound/AetherEngine). Everything runs on the main actor. It turns the engine's published state into `PlaybackEvent`s, each once per change, and owns the load task. The engine draws into its own view, so the port has no surface: the composition root hands `AetherPlayerSurface` to the UI as `Services.videoSurface`.

### Adding a provider

A provider is a folder under `app/Shared/Adapters/` with types that conform to ports. `Adapters/SkipDB/` is the example: `SkipDBSkipSegmentService` and its private response types, HTTP and decoding failures mapped to `SkipSegmentError`, and one line in `Services.live`. Features and views do not change. A provider for a port keyed by titles keeps results keyed by the same `MediaID`, so stream lookups still match.

### Strictness

Swift 6 with complete concurrency checking, `ExistentialAny` and warnings as errors. SwiftLint runs as a build tool plugin on every app and test build in strict mode (`.swiftlint.yml`). Force unwraps, force casts, `try!`, `@unchecked Sendable`, `nonisolated(unsafe)` and `assumeIsolated` fail the build unless disabled on the line with a reason. The `StremioTVTests` target compiles Domain and Features without the bridge or AetherEngine, so those layers cannot import an adapter.

### Platforms

`app/Shared` is compiled into both apps, including the screens in `app/Shared/UI`. They differ by platform only where input differs (`#if os(tvOS)` for focus sections, card buttons and the remote's commands). The platform folders hold only assets. Views parse text input into domain types before sending events.

### UI

`Theme.swift` holds the colors (`Palette`: canvas, surface, burgundy, red, text, secondary, and the subtitle preview's scene) and the sizes that differ between the TV and a window (`Metrics`). Nothing else names a color value. Text, secondary and surface get stronger under Increase Contrast. `TextLayout`, read as `@Environment(\.textLayout)`, is the one test for accessibility text sizes (Large Text on tvOS): shelves hold fewer lockups, labels wrap (`labelLineLimit()`) and the streams screen stacks its title above the list. The shared pieces are `AppLogo`, `Artwork` (an add-on image with a placeholder), `ProgressLine`, `PosterGrid` (rows of posters between the margins, for a genre and the library), `PosterCard` (a `.borderless` lockup on tvOS: focus lifts the poster and moves its name out of the way), `ContinueCard` (a `.card` lockup, captions below), `Shelf` (a titled sideways row whose lockups each take a column of Apple's grid, per `Lockup`, so the first and last line up with the margins), `ScreenTitle` (a screen's name drawn in its content and marked as a header; `.screenTitle(_:)` hides the tvOS navigation bar, which would pin the title over scrolled content), `SettingsPage` (an emblem beside a list, below its title), `ChoiceMenu` (a button naming the current value that opens its choices below it, current one checked and focused; it closes at once on a choice, on Menu or when focus leaves, and the screen draws it with `choiceMenus()` in its own bounds, because the tvOS focus engine does not move between rows that overflow their frame), `GlassList` (checkmarked rows on Liquid Glass, as tall as they are and scrolling past a maximum, for `ChoiceMenu` and the player), `ChoiceList` (a pushed list of checkmarked choices with the current one focused, for a setting), `SubtitlePreview` (the overlay over a sample scene, the emblem of Settings › Subtitles and of each style choice, where it shows the focused choice), `ValueRow` (a settings row that shows a value and still takes focus), `SegmentedButtons` (separate buttons sharing one capsule, for actions that exclude each other, such as Like and Love), `CancellableProgress` (a pushed screen's spinner with a Cancel that goes back, so the screen always has something to focus) and the player's `PlayerControls`, whose subtitles, audio and speed choices open in an `OptionsPanel`, a `GlassList` over the video, and `SubtitleOverlay`. No screen uses the system pull-down, SwiftUI's `Menu` or UIKit's `UIMenu`: on tvOS both keep focus in the menu for the 1.2 s of its closing animation, half a second after it has left the screen. Nor a segmented `Picker`, which on tvOS selects every segment focus crosses. The overlay draws the session's visible `SubtitleCue`s above the video and below the controls: text in the user's `SubtitleStyle` (size, font, weight, colors, outline, backing, opacity), sized and raised as fractions of the picture's height so the preview matches the player; bitmaps scaled to the fitted picture where the stream places them. Icons are SF Symbols; empty and error states use `ContentUnavailableView`. The logo (`AppLogo`, asset `Logo`) and the macOS and tvOS app icons, including the tvOS layered icon and Top Shelf images, are generated from `assets/logo.png` by `swift scripts/make-icons.swift assets/logo.png`; rerun it when the logo changes. Navigation is five tabs (Home, Library, Calendar, Search, Settings), each a `NavigationStack` driven by `Route` (`details`, `streams`, `genre`). Before anything is typed, Search shows a `Shelf` of recent searches and a `Shelf` of genres per content type; a genre opens a grid of `PosterCard`s under its title. Menu from anything below the search field scrolls back up and returns focus to the keyboard, then to the tab bar. Library shows a type `ChoiceMenu` and a sort `ChoiceMenu` above a `PosterGrid`; a long press on a poster removes it. Calendar shows a `Shelf` per day of upcoming episodes, each a wide card that opens the show. Details offers Add to Library beside Play, then Like and Love in one `SegmentedButtons` for a signed-in viewer. Settings › About › Share Logs shows a time range `ChoiceMenu`, the link as a `QRCode` (shared with sign-in) and as text, and stops sharing when it goes.

## Logging

`Log` (`app/Shared/Logging/Log.swift`) writes every line to the unified log (subsystem `com.ograbek.takane`, one category per area) and to `app.log`: `~/Library/Logs/com.ograbek.takane/` on macOS, `Library/Caches/Logs/` in the app container on tvOS. Each line starts with its local date and time to the millisecond (`2026-10-20T17:30:12.345+0200`); a message of several lines continues on lines without one. At launch the previous session's `app.log` moves to `sessions/<start>.log`, and sessions that ended over 7 days ago, the longest `LogWindow`, are deleted. `Log.export(_:at:)` returns the lines of a window across sessions under a header naming the version, the build and the window; `LogLines` holds the line format and the filter. Debug builds log everything as it is and echo to stderr.

Release logs name nothing personal, yet still show when two lines are about the same thing: "played A, then B, then A again". `Log.write` renders each line under `Redaction.current` bound to `Log.redaction`, so a `Redacted` value interpolated into it shows as `#` and 6 base32 characters of its HMAC-SHA256 (`#k3f9qa`): the same for the same value, different for different ones, across sessions. Outside log lines, as in text built for the screen, values show as they are. `Redacted` only wraps one value; `RedactedMask` (`app/Shared/Domain/RedactedMask.swift`, in Domain since it needs only Foundation and the domain's ids) holds every rule for values inside free text, and codes them with the same pseudonymizer, so a value reads the same code whichever way it reaches a line. `Log.write` runs `RedactedMask.line` on every line, which codes every web address (whole, host included, since even a host says which add-ons and debrid services the user chose: `https://torrentio.strem.fun/realdebrid=…/stream/movie/tt0063350.json` reads `#xlhujj`), every title id (`tt0063350`; `tt0944947:1:4` reads `#f46ip7:1:4`) and every long token (≥32 URL-safe characters), so text the app does not type, such as core's and Rust's logs, holds none either. In core's JSON (dispatches and events, `RedactedMask.json`) every string becomes a code except those naming core's own vocabulary (`action`, `model`, `field`, `type`, `resource`, `event` and a few more), and keys, numbers and booleans stay; in AetherEngine's lines (`RedactedMask.engineLine`), the origins it names without a scheme (`host:443`, `host=…`), file names and subtitle track names; and the bodies of core's failed responses are left out, since an add-on's error page can name it. Credentials are never logged: `Authenticate` dispatches log only their name. Content types, counts, durations, codecs, the decoder, the route, resolution, HDR and errors stay readable.

The codes are keyed by the install's `LogKey`: 12 random characters of Crockford's base32 (60 bits, no I, L, O or U) made on first launch and kept in the user defaults, shown as `XXXX-XXXX-XXXX` on Share Logs; typing it ignores case and dashes and reads O as 0 and I or L as 1. A value in the defaults that is not such a key is replaced with a new one. A shared log lets anyone test guesses offline, against its legend and against the codes of values they can guess, so `LogSecrets` first stretches the key with PBKDF2-HMAC-SHA256 (salt `takane-log-key-v1`, 600,000 rounds, about 0.1 s on Apple silicon), once per launch on a background queue; a line that codes a value before then waits for it. HKDF derives from the stretched key the HMAC key and an AES-GCM key. Share Logs shows the key hidden, as placeholder bars that hold none of it, until Show Log Key, and hides it again when the screen goes, so a photo of the screen does not give it away. Each code a session writes is recorded once, as code and value, in `app.legend` beside `app.log`, which archives and expires with it; a web address is recorded by its origin only and long tokens not at all (`RedactedMask.legendText`), so the legend reveals no debrid key. An export ends with `--- legend (encrypted) ---` and the codes it holds, sealed with AES-GCM. Without the key a log reveals nothing, even to someone trying every IMDb id; a user who sends the key privately lets the maintainer run `swift scripts/reveal-log.swift <log-file> <log-key>`, which prints the log with each code followed by its value.

What a log shows at the default level: under `ui` at info, every event a view sends (`LibraryFeature ← select(…)`, cut to 200 characters), tab switches (`tab → Search`) and route pushes and pops (`push details(movie/tt0063350)`, which a release log reads `push details(movie/#q5r4qa)`, `pop to root`); under `features` at debug, a state's change of case (`DetailsFeature loading → loaded`), by name only; core's dispatches and events under `core` and each request under `network` (`#4 → GET …`, `#4 ← 200 …`). Effects' answers and full states are trace. Rust logs only what Swift does not see, such as a response of the wrong shape, and core's storage reads and writes are trace. Rust `tracing` output and panics arrive as category `rust:<module>`; AetherEngine's own log (`EngineLog.handler`) arrives under `player` at debug level. Set `STREMIO_LOG_LEVEL` (`trace`, `debug`, `info`, `warning`, `error`) to change the threshold; the default is `debug`.

## Streams

`CoreStreamResults` maps `meta_details` to one source per add-on. It holds the streams the add-on embeds in its metadata for the video (`metaStreams`) first, then its answer to the stream request. Each candidate's player selection carries the stream's request and the metadata request of the first meta add-on that answered, or of the first one while none has. Core's `player` model loads the metadata from it and records progress against it, so a stream picked before the metadata arrives is still tracked. The mapping is tested in `StremioTVAdapterTests`.

Before display, filter the streams to supported sources:

| Source | Handling |
|---|---|
| `Url` | Play. If `proxyHeaders.request` is set, pass the headers to the engine (`LoadOptions.httpHeaders`). |
| `YouTube` | Out of scope for now. |
| `Torrent`, archives, `Nzb` | Hidden. |
| `External`, `PlayerFrame` | Hidden. |

## Player

AetherEngine demuxes each stream with FFmpeg and remuxes it into fMP4 for AVPlayer (route `loopback`), so VideoToolbox decodes, HDR and Dolby Vision reach the display, and Atmos passes through. Codecs fMP4 cannot carry are bridged (DTS and TrueHD to E-AC-3 or FLAC). What AVPlayer cannot play, and anything in the tvOS simulator, decodes in software (route `software`). Only the package's default traits are on. Core's `player` model owns playback state (progress, watched, next episode); `PlayerFeature` reports time (once per second), seeks, pause and end to it through `CorePlaybackTracker`. Core counts the time between two time reports as watched, so every engine seek, whatever started it, goes to core as `Seek` when it begins, before the position moves to its target. Until the seek lands the engine's clock can still read the old position, so `AetherPlaybackEngine` lets only the target through until then. Core copies progress into the library (and so continue watching) on pause, unload and every 180 s, not on every time update. On tvOS, AetherEngine releases the video pipeline and moves to paused when the app enters the background, so the pause report pushes progress before the system can suspend the app. The app adds no lifecycle reporting of its own.

The progress bar takes focus. A tap of left or right jumps one seek step (`SeekStep`, 10 s unless Settings › Playback says 5, 15 or 30), as the system player does. Taps in one direction within a second of each other make a `StepStreak`, whose distance shows beside the picture on that side ("+30s"). Left and right on the bare video step the same way and show the controls for 2 s with the progress bar focused, so further taps keep stepping; moving focus off the bar keeps them up as usual. The back and forward buttons jump one step (`.jump`). `.begin` reads the step with the languages and sends it back as `.preferencesRead` for its candidate, so the session holds it. Holding one scans at 2×: `PlayerFeature` pauses the engine and moves its own playhead (`Scan`, in `PlayerTimeline.swift`) every 0.25 s with an absolute seek, until select, play/pause or slowing below 2× resumes playback. Each press in the scan's direction doubles its rate up to 32× and each press against it halves it. The UI only tells a tap from a hold (0.5 s); on tvOS a UIKit view reads the arrows' press and release, which SwiftUI does not report for the Siri Remote.

A live channel (`PlayableID.liveChannel`, add-on type `tv`) has no timeline: `PlayerFeature` ignores jumps and timeline events for it, and the controls show a LIVE badge in place of the progress bar, the times and the skip buttons, so left and right on the bare video only show the controls. The engine reports no duration, so the session reports no progress and looks up no skip segments, and core keeps live channels out of continue watching.

Up next follows Stremio's own apps. Once core's `player` model loads the selection's meta item it finds the next episode (`nextVideo`), asks the selected stream's add-on for that episode's streams (`nextStreams`) and picks the one in the same `behaviorHints.bingeGroup` (`nextStream`). `PlaybackTracker.upNext(after:)` streams that as an `UpNext`, whose `stream` is a candidate built like `CoreStreamService`'s (same meta request, the next streams' request) when it plays here. `.watchUpNext` feeds it into the session as an `UpNextOffer` (`notFound`, `offered`, `dismissed`; rules in `PlayerUpNext.swift`). The player shows the card while the controls are hidden, from the notice before the end (`UpNextNotice`, core's `nextVideoNotificationDuration`, 35 s unless Settings › Playback says off, 10, 20 or 60) until the viewer acts on it, ahead of a skip button, and focus moves to Play Now. Play Now reports `NextVideo` (`.movedToNext`), then opens the next stream; without one it opens that episode's streams over the player. When an episode ends with the offer not dismissed and `bingeWatching` on (Settings › Playback › Autoplay Next Episode), Play Now happens by itself. A notice no `UpNextNotice` matches, set by another Stremio app, reads as 35 s and is kept until the user picks another.

`AetherPlaybackEngine` (`app/Shared/Adapters/Aether/`) maps the port onto the engine:

| Port | AetherEngine |
|---|---|
| `load` | `load(url:startPosition:options:)` in a task the adapter owns; a newer load or `stop` cancels it. `LoadOptions` carries the request headers and the preferred audio and subtitle languages. A cancelled load is not a failure; a failed one is reported once, from `state` |
| `setPaused`, `seek`, `setSpeed`, `stop` | `play`/`pause`, `seek(to:)` (relative seeks start from a seek still landing), `setRate`, `stop` |
| `select`, `turnOffSubtitles`, `addSubtitles` | `selectAudioTrack(index:)`, `selectSubtitleTrack(index:)`, `clearSubtitle()`, `addExternalSubtitleTrack`; `MediaTrack.ID.number` is the engine's track id |
| `loaded`, `paused`, `buffering`, `ended`, `stopped`, `failed` | `$playbackPhase` |
| `position`, `subtitles` | `clock.$currentTime`; cues from `$subtitleCues` whose PTS range holds `clock.$sourceTime` |
| `duration`, `videoSize`, `decoder`, `tracks` | `$duration`, the probed size times its pixel aspect, `$activeVideoDecoder`, the track lists and active indices |
| `diagnostics`, `snapshot` | route, decoders, audio delivery and `diagnostics.liveTelemetry`; `scrubThumbnail`, which decodes from the session's cache so a single-connection debrid link is not asked twice |

Subtitles come from two places, kept apart in the player's subtitles panel: the stream's own tracks ("Built-in") and the files the user's subtitle add-ons offer, one page per add-on grouped by language. Add-on subtitles are add-on driven only; the app calls no subtitle provider itself. A candidate's player selection carries a `subtitlesPath`, so core's `player` model asks every add-on with the `subtitles` resource. Core adds the file's `filename`, `videoSize` and `videoHash` from the stream's hints or from `VideoParamsChanged`, which `CoreSubtitleService` sends once it has fingerprinted the stream: the OpenSubtitles hash of the first and last 64 KiB, read with two range requests to the stream's host (`URLSession.fingerprint`). Add-ons that time subtitles to the file, such as Subtitle Sync, need these to tell this copy apart. A chosen file is registered with `addExternalSubtitleTrack`, fetched with its own headers and never the stream's, and selected; the adapter remembers which track id came from which URL, since the engine's track list does not say, and reports it as `MediaTrack.externalFile`. Until the viewer or a remembered choice picks subtitles, `PlayerFeature` shows the most preferred subtitle language that has any: the stream's own track, which the engine selects at load, else the first file in that language in add-on order (`Session.preferredSubtitles`). An add-on still answering holds the pick, and a later answer replaces it, since add-ons that time files to the stream answer again with its hash and put the best file first. The pick alone reports no choice to the tracker.

Track choices are remembered per title through core's `StreamsBucket`. When the viewer picks audio, subtitles (built-in, an add-on's file or off) or a speed, `PlayerFeature` reports everything playing now as `TrackChoices` (`PlayerTrackChoices.swift`), and `CorePlaybackTracker` sends it as `StreamStateChanged`: an embedded track by the engine's number and its language, an add-on file by its URL, the speed as `playbackSpeed`. Core replaces the whole `StreamItemState`, so the adapter starts from the player's current `stream_state` and keeps the keys the app does not manage (delays, subtitle size, player type). Core saves it only once its player model has loaded the title's metadata, and "off" is saved as no subtitle track, which the next play reads as nothing chosen. On load core exposes the saved state as `stream_state`, from this video or the latest of the 30 before it: the same stream keeps everything, a stream in the same binge group keeps the speed and the tracks it can match by language (embedded subtitles only), any other keeps only the speed. `PlaybackTracker.remembered` yields it once for the candidate, and the session's `Restore` (awaiting, pending, settled) applies it once the tracks are known: a track by number and language, else the first in its language, and an add-on file once an add-on offers its URL. Saved choices win over the language preferences the engine loaded with. Any choice the viewer makes first settles the restore, and choices for another candidate are dropped.

Subtitles are drawn by the app. Text cues arrive as styled runs (`SubtitleText`): libavcodec turns SRT, WebVTT and ASS tags into the same runs, so bold, italic, underline and strikethrough always show. With file styling on (`SubtitleStyle.usesFileStyling`), a run's color and font replace the user's, and a cue's ASS `\an` / `\pos` placement puts it at an edge, corner or point of the picture; otherwise every text cue joins one block above the bottom edge. A run's ASS font size is ignored, so text keeps the user's size. Bitmap cues (PGS) keep their position.

Wired from core's settings: `audio_language` and `secondary_audio_language`, `subtitles_language` and `secondary_subtitles_language` (as `TrackLanguages`, each a `PreferredLanguages` or nil), `subtitles_auto_select` (off reads as no subtitle languages; choosing Off writes it false), `seek_time_duration` (as `SeekStep`; a value no step matches reads as 10 s and is kept until the user picks another), the subtitle style (`subtitles_size`, `subtitles_font`, `subtitles_bold`, `subtitles_offset`, the colors, `subtitles_opacity` and `ass_subtitles_styling`, as `SubtitleStyle`), and `hide_spoilers` (as `Preferences.hidesSpoilers`; on, each unwatched episode card blurs its still and leaves out its overview), mapped in `CoreGeneralSettings` (audio, seek and spoilers) and `CoreSubtitleSettings`, both tested in `StremioTVAdapterTests`. A font name the app does not know reads as the system font and is kept until the user picks another. Not wired: `seek_short_time_duration` (a keyboard shortcut with no remote equivalent) and `hardware_decoding` (the engine picks the route itself).
